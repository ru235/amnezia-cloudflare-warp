## 1. Создать бота

1. Откройте [@BotFather](https://t.me/BotFather) в Telegram.
2. `/newbot` → имя → username (должен заканчиваться на `bot`).
3. Скопируйте токен вида `123456789:AAH...`.

Токен — это пароль от бота. Не публикуйте его и не коммитьте в git.

## 2. Узнать chat id

**Способ А, через @userinfobot:** напишите [@userinfobot](https://t.me/userinfobot), он ответит числом — это ваш chat id (у личных чатов он положительный, у групп — отрицательный, например `-1001234567890`).

**Способ Б, через API:**

1. Напишите своему боту любое сообщение (`/start`).
2. Выполните:

```bash
curl -s "https://api.telegram.org/bot<TOKEN>/getUpdates" \
  | grep -o '"chat":{"id":[-0-9]*' | head -1
```

Если ответ пустой — бот ещё не получал сообщений, напишите ему и повторите.

> Для групп: добавьте бота в группу, дайте право писать, отправьте сообщение с упоминанием бота, затем повторите запрос.

## 3. Включить в проекте

Интерактивно (спросит токен и chat id):

```bash
sudo ./install.sh --telegram
```

Без вопросов:

```bash
sudo ./install.sh --telegram \
  --token '123456789:AAH...' \
  --chat 123456789 \
  --bot-role active
```

Токен и chat id также можно передать через переменные окружения:

```bash
export TELEGRAM_TOKEN='123456789:AAH...'
export TELEGRAM_CHAT=123456789
sudo -E ./install.sh --telegram
```

Установщик создаст `/etc/warp-telegram.env`:

```bash
TG_TOKEN=123456789:AAH...
TG_CHAT=123456789
```

Права `600`, владелец root. Больше ничего править не нужно: скрипты читают этот файл при каждом запуске.

### Включить вручную, без переустановки

```bash
install -m 600 /dev/null /etc/warp-telegram.env
cat > /etc/warp-telegram.env <<'EOF'
TG_TOKEN=123456789:AAH...
TG_CHAT=123456789
EOF

systemctl enable --now warp-bot.service
sudo /usr/local/sbin/warp-daily-report.py   # проверить отправку
```

Монитор и отчёт подхватят файл на следующем запуске (в течение минуты / в ближайшее расписание).

## 4. Проверка

```bash
# токен валиден?
curl -s "https://api.telegram.org/bot$(grep TG_TOKEN /etc/warp-telegram.env | cut -d= -f2)/getMe"

# отчёт с картинкой
sudo /usr/local/sbin/warp-daily-report.py

# бот отвечает?
sudo /usr/local/sbin/warp-bot.py --test   # печатает тексты без отправки
systemctl status warp-bot.service --no-pager
```

После запуска бота отправьте ему `/start`.

## 5. Команды бота

| Команда | Действие |
|---|---|
| `/menu`, `/start` | Главное меню с кнопками |
| `/status` | Сводка по всем серверам |
| `/s1`, `/s2` | Детали сервера: WARP, IPv4/IPv6, Amnezia, онлайн, последний клиент, смены IPv4, диск, uptime |
| `/warp` | Состояние WARP и адреса |
| `/report` | Собрать и отправить отчёт с графиком |
| `/ping` | Задержка до серверов и Telegram API |
| `/help` | Список команд |

Кнопки: «📊 Отчёт», «🔄 Обновить», серверы, «🌐 WARP», «📡 Ping», «⬅️ В меню».

`/report` запускает `warp-daily-report.py` от имени сервиса. Картинка приходит отдельным сообщением, потому что бот не может редактировать фото на месте.

## 6. Алерты

Монитор проверяет состояние раз в минуту. Уведомления приходят после **5 минут** непрерывной проблемы, а не с первого сбоя — чтобы не спамить при перезапусках.

| Событие | Условие | Восстановление |
|---|---|---|
| 🔴 Пир недоступен | TCP/22 без ответа 5 минут | 🟢 «снова доступен», простой в минутах |
| ⚠️ WARP не подключён | `warp-cli status` без `Connected` 5 минут | ✅ «снова подключён» |
| ⚠️ Контейнер не запущен | нет `amnezia-awg*` 5 минут | ✅ «снова работает» |
| 💾 Мало места | диск ≥ 90% | флаг снимается при < 85% |
| ⚠️ Ответы уходят в WARP | bypass-маршрут перехвачен, самовосстановление не помогло | ✅ «маршруты восстановлены» |

Алерт про маршруты — самый важный: он означает, что SSH/Caddy/AWG могут перестать работать. Скрипт сначала пытается исправить правило сам (`ip rule` → приоритет 10), и только потом пишет.

## 7. Два сервера и резервный бот

Правило: **один токен — один активный поллер**. Если запустить `getUpdates` с одного токена на двух серверах, Telegram начнёт отдавать `409 Conflict`, и бот будет «моргать».

Схема:

```bash
# основной сервер
sudo ./install.sh --telegram --bot-role active

# резервный сервер
sudo ./install.sh --telegram --bot-role passive
```

- `active` — бот работает всегда (`warp-bot.service`).
- `passive` — бот выключен; `bot-guard.timer` раз в минуту проверяет основной сервер по TCP/22. Если тот недоступен 5 минут подряд — запускает бота у себя. Когда основной возвращается — останавливает.
- `none` — бота нет, но алерты и отчёты работают.

На резервном сервере должен быть тот же `--peer-ip`, что и в мониторинге, иначе guard не знает, кого проверять.

Отчёты при этом отправляют **оба** сервера независимо — так и задумано: если один упал, второй продолжит присылать свой.

## 8. Безопасность

- `/etc/warp-telegram.env` — `chmod 600`, в git не попадает (`.gitignore`).
- Бот реагирует только на сообщения из `TG_CHAT`. Чужой чат игнорируется полностью.
- Бот не принимает произвольные команды shell: только фиксированный набор.
- Если токен утёк — `/revoke` у @BotFather, затем обновите файл и перезапустите сервисы.
- Для группы дайте боту минимум прав: читать сообщения и отправлять их.

## 9. Отключение

Оставить мониторинг и отчёты, убрать бота:

```bash
sudo ./install.sh --telegram --no-bot
```

Полностью убрать Telegram:

```bash
systemctl disable --now warp-bot.service bot-guard.timer
rm -f /etc/warp-telegram.env
```

После этого монитор перестанет отправлять алерты, а отчёт будет только сохранять PNG в `/var/lib/warp-monitor` — маршрутизация и ротация не затрагиваются.

## Если бот молчит

1. `systemctl status warp-bot.service` и `journalctl -u warp-bot.service -n 50`.
2. `curl .../getMe` — токен валиден?
3. `getUpdates` вручную: если `409 Conflict`, где-то запущен второй экземпляр (второй сервер, старый процесс, локальный запуск).
4. `grep TG_CHAT /etc/warp-telegram.env` — совпадает с чатом, откуда пишете?
5. `warp-bot.py --test` — проверьте, что метрики собираются, а не падает SSH к пиру.

Больше симптомов — в [TROUBLESHOOTING.md](TROUBLESHOOTING.md).
